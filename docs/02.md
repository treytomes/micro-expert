# The expert can plug its own holes.

Let's say that you want to allow an AI to research a problem we don't have an answer for yet.  There are countless paths it could pursue.  How should it decide which way to go?  Which path has the highest value?

My theory is that the highest value path can be chosen by giving the model access to an expert system with an S-P-O graph.  The highest value next steps are to answer questions that link together sections of the graph that previously had no path between them, or to expand the frontier of the graph.

Some questions, like the problem of continual learning in AI, may not be provable right away, but expanding the graph of known facts will always have value.

## Identifying the missing facts?

The interesting queries are the ones that fail; the times when backwards chaining comes back empty.  The answer isn't "yes" or "no", it's "this graph has a hole in it".  The useful answer in this case isn't the empty result set, it's the shape of the hole.

Our example model is small enough to hold in your head.  A fact is one ground S-P-O triple, `parent-of(susan, tim)`; put a `?p` in it and it becomes a question.  A rule is a head and a body:

```
uncle-of(?x, ?y) <- parent-of(?p, ?y), sibling-of(?x, ?p), has-gender(?x, male)
```

When the search fails, the same machinery runs backwards: one candidate for every path where the goal could still be proved, and each rule body walked left to right.  A condition the search can meet is crossed off, carrying a value forward only when every proof agrees on it - a report never picks one of two parents just to look concrete.  The conditions it can't meet are facts to add, in symbolic form, and a later one that those facts would settle is printed as a check instead:

```
Query: uncle-of(oliver, ?p)
  no solution found at depth 8
  A solution would need one of these:
    a fact like uncle-of(oliver, ?p)
    through rule uncle-of(?x, ?y) <- parent-of(?p, ?y), sibling-of(?x, ?p), has-gender(?x, male)
      parent-of(?p', ?p)
      sibling-of(oliver, ?p')  (checked once the facts above exist)
    (a name ending in ' is the rule's own variable, not one you asked about)
```

This is the case that matters for the picture above.  Every one of those conditions is separately provable - parent facts exist, Oliver has siblings, Oliver is male - and Oliver is still nobody's uncle: three conditions that each look satisfied prove nothing together.  That's why a body is judged as a body, and what comes back is the edge that is really missing: Oliver's siblings exist, but none of them has a child, so the fact to add is `parent-of(?p', ?p)` for one of those siblings.  Add `parent-of(clara, zed)` and the query answers `uncle-of(oliver, zed)`.

When the session at the prompt picks one of these to ask about, it ranks them, and the ranking is an opinion: a rule's fact before the query's own shape, because asserting the answer teaches the graph one instance and nothing else.  What's left is a short list of questions, each one located: `parent-of(?p', susan)` isn't "find out about the family", it's "who are Susan's parents?", with a place to put the answer.

That's the frontier to point a model at.  Each entry is cheap to check, and the answer goes exactly where the hole was - the graph gains an edge, the next report comes out different, and the loop runs again.  Continual learning, one missing fact at a time, which is why the report belongs in the engine rather than on the nice-to-have list.  It's also bounded by the same `--depth` as the search, so "missing" means missing at depth 8.

## The algorithm

The honest way to describe the report is that it is not a second program.  It is the search, run again with the answers thrown away.

`proveGoals` walks the rules whose heads meet the goal and returns the proofs it found.  `needsFor` walks the same rules, in the same order, from the same bindings, and where `proveGoals` would have recursed into a body it asks the same question of that body - except that a condition with no proof stops being a dead end and becomes a line of output.  Unification, standardization apart, the cycle guard and the depth counter are all the same code.  Stripped to the shape of the recursion, the two differ only in what they do with a derivation:

```
proveGoals                          needsFor
  for matched in matchingFacts        options = [a fact like the goal]  (if none matches)
    mergeAnswer(...)                  for candidate in matchingRules
  for candidate in matchingRules        for result in bodyResults
    for proved in proveConditions         if result.needs.len > 0
      mergeAnswer(...)                      options.push(result)
```

That is the whole idea, and it is why the feature was cheap: the hard parts - what a rule means, when two patterns meet, when a chain loops - were already solved once, for answering.  The report needed the answers' bookkeeping to be thrown away, not a new reasoner.

Sharing the depth counter is worth a sentence of its own, because it is what keeps the report honest.  `depth - 1` per rule level means `--depth 8` bounds the report at eight rule levels as well, so "missing" means missing from where the search actually stood, not from some ideal graph with no limits.  At `--depth 0` the report degenerates on purpose: facts only, so the only thing it can offer is a fact shaped like the question.

Walking a body is where the details are.  Conditions are taken left to right, carrying bindings, and each one lands in one of three states.  Proved, it is crossed off and its bindings go forward.  Unproved, it becomes a fact to add, printed in symbolic form with whatever the body has bound so far substituted in.  Or - the case that took me three tries - unproved *and* undecidable, because a fact asked for earlier in the same body would bind the variables it mentions.  There is no way to look that one up yet, and no honest way to say it needs a fact of its own either, so it prints as a check: `(checked once the facts above exist)`.  Two variables of bookkeeping, `newVars` for what the missing facts would bind and `coveredBy` for testing a condition against it, and the report stops asking for the same value twice.

The next detail is the one I would defend hardest.  A condition can have several proofs, and the proofs can disagree: every child in this family has two parents, so `parent-of(?p, tim)` holds twice over, once with `?p` as bill and once as susan, and nothing about the question says which.  The report carries forward only the bindings *every* proof agrees on (`agreeingBinds`), so a line stays symbolic exactly as long as the graph fails to force a value.  It would have been easy - and wrong - to take the first proof and print `parent-of(bill, tim)` as the missing fact: the gap would look narrower than it is, and a reader would go looking for one particular fact when either would do.  Values that are settled do still show: the goal's own terms, anything the search pinned down, and anything the session has been told, which is substituted into the report before printing - the `sam` in the block above came from the prompt, not from the search.

Then there is the case that made the report worth writing.  A body whose conditions are each provable on their own, but never all at once, gets walked leniently first: each condition is checked against the graph and crossed off, and at the end the body claims it needs nothing - while the search that prompted the report came back empty.  Rather than print a rule that needs nothing for a query that fails, the body is read a second time in a stricter mode (`reportOpen`): a condition whose proofs leave some variable open is reported as a fact to add instead of being crossed off.  That is the three-line block in the previous section, and it is the difference between "nothing is missing" and "nothing is missing individually".  A body has to be judged as a body.

What the report will not do is assert anything.  Each alternative is independent - the header says *one of these*, not all of them - and nothing is added to the graph by being printed; only the session, with a human at the prompt, turns an alternative into a fact.  The search is also still goal-directed: the report only walks rules whose heads meet the question and conditions the body actually has, so asking about a hole in one branch does not walk the whole knowledge base.  It is bounded work, sized by the question.

Two loose ends are worth naming, because both are visible from the outside.  Variables that came out of `standardizeApart` carry a suffix (`?p_3`), so the report relabels them before printing: the query's own names are claimed first, then a rule's variable that would read the same gets a prime, `?p'`, with a footnote line explaining it.  And identical alternatives are collapsed by their printed block, so two rules that would need exactly the same facts print one block between them.  The paint lives outside all of this - the report returns plain text plus role names, and the style table decides the colors - which is why `NO_COLOR` leaves the algorithm untouched and the same lines come out of a redirected run.

The cost of the mirror is honesty rather than intelligence: it can tell you where the graph has no edge, and it cannot tell you which edge is worth the most.  That judgement is the part I want a model for.
